# 0028 — Game screen flow, stage level scenes and per-mode tools

- Status: accepted
- Date: 2026-09-30
- Implements: issue #43 and the owner's instruction of 2026-09-30 (stop #42, build level scenes,
  let 2D menu scenes choose what to do, and separate what each mode can do)
- Extends: ADR 0007 (input ownership), 0023 (declarative tasks), 0025 (stage targets and outcomes).
  Graph authority, physics, board/runtime separation and stage schema v2 remain unchanged.

## Context

The owner opened the app as a user and could not tell what to do. There was one scene
(`scenes/main.tscn`) and one 4 m floor. Stages were data that swapped the robot on that same
floor; there was no title, stage selection, loading, briefing or result screen. Parts, examples,
AI lab, challenge authoring and the flag mission were visible at once. The 2026-09-30 design note
said Stage and Lab "use the same workshop", which was meant for the editing tools but was built
as "one screen for everything".

## Decision

- `scenes/app.tscn` is the main scene and routes between screens. Menus are separate 2D scenes
  in `scenes/screens/` (title, stage select, examples, loading). They only choose the next action.
- Each chosen action instantiates a fresh workshop (`scenes/main.tscn`) with a `session`:
  `stage` (a level), `lab` (free building and challenge authoring) or `example` (a finished
  robot). An empty session keeps the full legacy workshop used by existing tests.
- A stage is a level scene plus a stage definition. `StageLevels` lists playable stages in order
  and points to `stages/<id>/level.tscn` and a `StageCatalog` entry. The level supplies ground,
  props, visual goal markers, a play area for the camera and the floor height. Markers never
  collide and never enter the learner's ConnectionGraph; physical stage objects that affect the
  goal (for example `stage_wall`) stay graph parts as before.
- Level scenes are generated by `tools/godot/make_levels.gd` and may then be edited in the Godot
  editor. This is an owner-approved exception to "humans compose `.tscn`" for level scenes only.
  Once a level is hand-tuned, it is no longer regenerated.
- Stage mode shows only the tools that stage needs: its tabs, allowed parts (none for prebuilt
  robots), run/reset, hint and mission. The owner asked for a focused screen (2026-09-30): the
  workspace header, footer and edit tools are hidden; a single goal card (back, stage, goal,
  measured value, hint, fixable errors) sits top-left and the program panel on the right. While
  an attempt runs, the run button becomes "Reset robot". Projects, AI lab, example robots, challenge authoring,
  the physics toggle and the old flag panel are hidden. Lab hides the stage picker and examples;
  examples hide authoring.
- `StageHud` shows the briefing first, a goal card with the live measured value, and a result
  window. Clear and failure come only from the evaluator's observed outcome (ADR 0025).
- When a learner program finishes while the attempt is still running, the attempt ends as
  `not_met` / `program_finished` after the longest hold time plus 1.5 s, instead of waiting for
  the 60 s time limit. Late callbacks cannot replace a terminal result (execution ID check).
- Clear records live in `user://progress.json`, separate from projects and preferences. The
  stage order is a recommendation; nothing is locked.

## Consequences

Tests and older entry points that instantiate `main.tscn` directly keep the legacy workshop.
Level scenes are part of the stage's starting environment; they are included in the local proof
identity through `res://stages/` resource hashing. Imported challenge files still load on the
default floor because the file format has no level reference; adding one needs a new schema
version. Only three stages are playable; the other planned names are shown as "coming soon".
Block editing UX, part thumbnails and appearance customization remain separate work.
